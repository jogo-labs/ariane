## Accessibilité

### Pris en charge automatiquement

- Élément `<dialog>` natif avec `role="dialog"`, `aria-labelledby` et `aria-modal`.
- Quand `without-header` est actif, `aria-label` (basé sur `label`) remplace `aria-labelledby` — le nom accessible reste garanti même sans header visible.
- Le focus est déplacé à l'ouverture sur l'élément portant `autofocus`, ou à défaut sur le premier élément focalisable, ou sur le bouton de fermeture si aucun n'est présent, ou sur le `<dialog>` lui-même si le header est absent — conforme
    <WcagRef
        criterion="2.1.2"
        summary="No Keyboard Trap : le focus clavier peut toujours quitter un composant via les touches standard (Escape, Tab)."
    />
- Le focus est restauré sur l'élément déclencheur à la fermeture.
- Le scroll du `<body>` est bloqué à l'ouverture et restauré à la fermeture, y compris avec plusieurs dialogs empilés.
- La touche Escape passe par `ar-dialog-hide` : la fermeture peut donc être interceptée avec `event.preventDefault()` — comportement prévisible conforme
    <WcagRef
        criterion="3.2.2"
        summary="On Input : modifier un composant UI ne doit pas provoquer de changement de contexte inattendu sans en avertir l'utilisateur au préalable."
    />
- Quand une fermeture est bloquée, le composant secoue visuellement le dialog et annonce automatiquement `prevented-message` via la zone d'annonce globale de la librairie.
- Les animations sont désactivées si `prefers-reduced-motion: reduce` est actif.

### À votre charge

- **Fournir un `label` descriptif.** Un fallback `Dialogue` existe, mais il doit rester un filet de sécurité, pas le libellé final du composant. Un avertissement est émis dans la console si ni `label` ni `slot="label"` ne sont fournis.
- **`without-header` retire le bouton de fermeture.** `label` devient requis (le slot `label` HTML est sans effet dans ce mode), et un moyen de fermeture doit rester accessible — `close-on-backdrop`, ou un bouton `data-ar-dialog="close"` (ou un `<form method="dialog">`) dans votre contenu. Un avertissement est émis en développement si aucun n'est détecté (Échap reste toujours disponible).
- **Toujours proposer une issue claire.** Le backdrop est statique par défaut : prévoir un bouton de fermeture visible ou un bouton `data-ar-dialog="close"`.
- **Si vous bloquez la fermeture, renseigner `prevented-message`.** Le message doit expliquer quoi faire pour continuer ou confirmer l'action.
- **Piloter le focus initial si nécessaire.** Posez `autofocus` sur l'élément qui doit recevoir le focus à l'ouverture — utile par exemple pour un champ de saisie dans un drawer.

## Utilisation

### Ouvrir et fermer sans JavaScript : `data-ar-dialog`

Plutôt que de piloter `open` en JavaScript, un élément cliquable porte `data-ar-dialog="verbe#id"` — un écouteur global au niveau du document intercepte le clic. Le verbe dit l'action, l'`id` (après le `#`) désigne le dialog visé :

- `open#id` ouvre le dialog d'`id` donné ;
- `close` ferme le dialog qui contient le bouton (le plus proche, si des dialogs sont imbriqués) ;
- `close#id` ferme un dialog précis, où que se trouve le bouton.

Le `#` sépare le verbe de l'`id` au premier `#` rencontré : un `id` qui contient `:` ou `#` (par exemple celui que génère `useId()` de React, `:r0:`) fonctionne tel quel. Un verbe inconnu, un `open` sans `id` ou un `id` introuvable émettent un avertissement en développement.

```html
<button data-ar-dialog="open#confirm-dialog">Supprimer</button>

<ar-dialog id="confirm-dialog" label="Confirmer la suppression">
    Cette action est irréversible.
    <div slot="footer">
        <button data-ar-dialog="close">Annuler</button>
        <button data-ar-dialog="close" value="confirm">Confirmer</button>
    </div>
</ar-dialog>
```

Le `value` du bouton cliqué devient `dialog.returnValue`, comme pour un `<dialog>` natif : c'est ainsi qu'on distingue une confirmation d'une annulation.

### Formulaire dans un dialog : `<form method="dialog">`

Un `<form method="dialog">` placé dans le dialog le ferme à sa soumission, comme dans un `<dialog>` natif. Le bouton qui a soumis le formulaire fournit `returnValue` (sa `value`) et `detail.source`. La validation du navigateur s'applique avant la fermeture : un champ `required` vide empêche la soumission, sauf pour un bouton `formnovalidate` (« Annuler »).

```html
<ar-dialog id="edit-dialog" label="Renommer">
    <form method="dialog">
        <label>Nom <input name="name" required /></label>
        <button value="cancel" formnovalidate>Annuler</button>
        <button value="save">Enregistrer</button>
    </form>
</ar-dialog>
```

### Personnaliser le header

Le conteneur du slot `header-actions` expose son propre `::part(header-actions)`, indépendant du layout titre/fermeture — utile pour définir un espacement entre plusieurs actions sans affecter le reste du header :

```css
ar-dialog::part(header-actions) {
    gap: 0.5rem;
}
```

Pour masquer visuellement le titre sans casser le nom accessible du dialog, masquez `::part(title)` avec la technique sr-only standard — pas `display: none` ni `visibility: hidden`, qui peuvent faire perdre le nom accessible calculé via `aria-labelledby` dans certains navigateurs :

```css
ar-dialog::part(title) {
    position: absolute;
    width: 1px;
    height: 1px;
    overflow: hidden;
    clip: rect(0, 0, 0, 0);
    white-space: nowrap;
}
```

Cette technique sort le titre du flux (`position: absolute`), ce qui rompt le `margin-inline-end: auto` utilisé par le composant pour aligner `header-actions` et le bouton de fermeture en fin de header. Complétez avec `justify-content` sur `::part(header)` pour conserver cet alignement :

```css
ar-dialog::part(header) {
    justify-content: flex-end;
}
```

Le slot n'est pas limité à des boutons isolés — un seul enfant slotté peut lui-même porter son
propre layout interne (actions à gauche, pagination à droite, titre sr-only…). Voir la variante
« Header avancé » pour une démonstration complète.

Pour retirer entièrement le header, voir la variante « Sans header ».

### Cycle d'événements

Tous les événements portent `detail: { id, source, returnValue }` :

- `id` : l'`id` du dialog ;
- `source` : l'élément à l'origine du changement, c'est-à-dire le bouton `data-ar-dialog` cliqué ou le bouton qui a soumis un `<form method="dialog">` ; le dialog lui-même pour Échap, le clic sur le backdrop ou une assignation de `open` (peut être le bouton de fermeture interne du header, `part="close-button"`) ;
- `returnValue` : la `value` du bouton à l'origine de la fermeture, sinon `''`. Elle est aussi lisible sur `dialog.returnValue` après la fermeture, remise à `''` à l'ouverture suivante et quand la fermeture est annulée.

Un seul geste de fermeture produit donc un seul événement `ar-dialog-hide`, que le dialog soit fermé par « Annuler », « Confirmer », Échap ou un formulaire : c'est `returnValue` (ou `source`) qui les distingue. La liste complète des événements, avec leur annulabilité, est dans la [Référence API](#reference-api).

```js
document.getElementById('confirm-dialog').addEventListener('ar-dialog-hidden', (e) => {
    if (e.detail.returnValue === 'confirm') console.log('Confirmé, dialog :', e.detail.id);
});
```

### Fermeture différée

Pour enregistrer avant de fermer, annulez `ar-dialog-hide` et posez `pending` dans le même gestionnaire. Le dialog reste ouvert, annonce l'attente au lieu d'un blocage et ignore les nouvelles tentatives de fermeture. Une fois la réponse reçue, levez `pending` puis fermez, ou laissez le dialog ouvert en cas d'échec :

```js
dialog.addEventListener('ar-dialog-hide', async (e) => {
    if (e.detail.returnValue !== 'save') return; // Annuler, Échap, backdrop : on laisse fermer
    e.preventDefault();
    dialog.pending = true; // avant le premier await
    try {
        await save();
        dialog.open = false; // nouvelle fermeture : returnValue est revenue à '', elle passe
    } finally {
        dialog.pending = false;
    }
});
```

Le dialog lit `pending` dès le retour du gestionnaire : posez-le directement sur l'élément, avant tout `await`. Un `pending` que votre code applicatif ne reflète sur l'élément qu'après coup (liaison d'attribut mise à jour au prochain rendu, par exemple) arrive trop tard : le dialog a déjà traité l'annulation comme un blocage, avec sa secousse et son annonce. Une liaison peut ensuite refléter l'état affiché, mais elle ne remplace pas cette écriture.
